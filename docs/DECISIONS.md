- 2026-11-07: **Supabase (Entrega 1): sincronização por diff em vez de reescrever os componentes.** Contexto: o repositório e os componentes eram síncronos. Alternativas: (a) tornar toda escrita assíncrona e adaptar ~14 componentes; (b) manter o repositório e trocar só a persistência. Decisão: (b). O store tem duas origens, `local` (localStorage, o modo demo de antes) e `supabase`, escolhidas pela presença das variáveis. No modo Supabase cada operação atualiza a tela (otimista), calcula o diff do estado (`src/lib/data/sync.ts`) e o envia a uma server action que valida com Zod (`row-schemas.ts`, derivados dos schemas dos formulários) e chama `apply_changes(jsonb)` numa transação. A fila é sequencial; numa falha ela para e o usuário escolhe reenviar ou descartar, voltando ao último estado confirmado. Motivo: regras de negócio num só lugar, nenhuma regressão visual, atomicidade e validação no servidor.
- 2026-11-07: **Modelo de dados.** 10 tabelas com `owner_id default auth.uid()`. Exclusões usam `on delete set null (coluna)` ou `cascade` nos filhos (tarefas, itens, pagamentos). Datas em `timestamptz`, valores em `numeric(12,2)`, enums como `text` + `check`, preferências como `jsonb` (1 linha por usuário). RLS em todas as tabelas, só para `authenticated`; `anon` sem privilégios; `apply_changes` é `security invoker` (RLS vale dentro dela), com tabelas de listas fixas e `search_path` vazio.
